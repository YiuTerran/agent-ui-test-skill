# API覆盖设计与缺口校验

在新增API用例、逐模块补齐或验收覆盖充分性时读取。已有回归按原case执行。设计覆盖、可发现的自动化实现、真实执行结果分别统计；新增条数和接口命中率不能代替场景覆盖。

## 从契约和业务链建立清单

先冻结本轮范围及需求、接口契约和代码版本，盘点实际路由及方法，再读DTO、认证/授权、业务判断、仓储和下游调用。前端case可复用业务语义，但API清单还要覆盖UI无法构造的输入、直接访问和调用顺序。自动生成接口清单之后仍需阅读业务处理；源码分析说明可观察的业务分支，不能以方法行数推导HTTP覆盖率。

每个接口建立以下映射，编码时同步维护：

| 对象 | 必须回答 |
| --- | --- |
| 正例 | 最小合法输入、完整输入、契约不同的可选字段/模式、成功后的真实状态及副作用 |
| 负例 | 哪个规则拒绝、如何越过更早的校验到达该规则、HTTP与业务错误、哪些数据和下游效果应保持不变 |
| 普通分支 | 入口条件、if/else/switch的各结果、有效状态转换、查询/持久化/下游结果及case映射 |
| 动态输入 | 等价类、边界、风险维度、代表组合、不可行约束及未覆盖范围 |
| 联合旅程 | 哪些服务生产和消费同一业务身份、数据或状态，如何在下游独立验证和清理 |

模块内逐接口分析后再按依赖顺序编码；代表流程先验证fixture及清理，之后继续获准的分支和旅程。共享准备逻辑不合并独立拒绝场景的结果：各自可失败的输入行生成独立Playwright test。一个test内的多步适用于同一业务旅程。

## 普通逻辑尽可能覆盖所有业务分支

对有限、可到达且在范围内的分支逐项建立case，而非只选择一个成功和一个失败。分支清单同时含正常、替代、拒绝和可观察异常路径：

- 参数按实际规则区分省略、null、空值、空白、类型/格式、枚举、上下界及越界；数字、长度、时间和精度分别按业务计数口径选择边界。新增、更新、批量入口分别追踪其校验链。
- 复合判断按决策表列有效条件组合，保留每个原子条件能独立改变结果的组合；多个拒绝条件同时触发时先分离，避免全被第一层校验遮住。高风险组合补充优先级断言。
- 业务覆盖唯一性作用域、存在/不存在/外租户资源、引用约束、状态正反转换、空/单条/多条结果、排序/筛选交集/分页、批量全部成功/部分失败、幂等和重复动作的实际语义。
- 读取和写入分别验证权限与租户隔离；外租户目标必须确实存在。权限拒绝的请求在其他参数上有效，不能用格式错误请求冒充鉴权分支。
- 写入正例回读字段、关系、持久化和下游消费；负例回读原状态和受保护对照，确认没有部分更新或意外下发。清理后没有数据不等于业务过程没有写入。
- 对超时、依赖失败、事务回滚、重试/补偿等可观察结果，使用获准环境或隔离替身验证具体责任。离线故障注入单列，不能登记成真实HTTP通过；无法安全触达的分支记阻塞及所需条件。

`branch_assessment.completeness=complete`表示当前已阅读范围的分支盘点与映射完整；缺少分支或可执行条件用partial。not_applicable只适用于确无相关业务分支并给出依据，不能把难测分支标成不适用。没有源码时继续契约黑盒测试，保留实现分支未核实。该清单不是JaCoCo等运行时分支覆盖率。

## 动态接口按代表场景覆盖，有限分支仍逐项检查

命令参数取决于物模型、规则编排取决于组件和图结构时，输入空间通常开放。将有限控制逻辑与开放组合拆开：模式切换、鉴权、模型查找、状态判断、超时和拒绝等普通分支仍逐项覆盖；任意JSON、任意组件参数和任意图只做有依据的代表覆盖。

1. 从真实schema和消费实现划分等价类。记录各维度的代表值及含义，包含常规值、适用边界、无效值。没有数值或有序边界的维度可以说明不适用，不制造无意义的边界case。
2. 先保留主要成功旅程，再选择会改变校验、转换、路由、状态或副作用的典型结构和风险组合。明确哪些交互必须覆盖，而非仅把“interaction”写在标题里。
3. 小型有限决策表可全组合；独立维度较多时用约束下的pairwise减少组合，并额外保留已知高风险三维或更高阶组合。有强业务依赖时直接用决策表或risk_based，不能用pairwise替代关键组合。
4. 区分合法但未测试的组合与契约上不可能的组合。前者登记缺口；后者通过有来源的约束排除。被接口明确拒绝的无效组合也是可测试输入，不能用“不可行”删掉负例。
5. 每个选择绑定具体场景、case和断言，列出未测代表值、交互和剩余输入空间。full仅表示声明的有限代表集合全组合，不表示开放参数完全覆盖。

典型维度的选取示例：

| 接口形态 | 代表维度与场景 |
| --- | --- |
| 动态命令下发 | 实际支持的值类型/嵌套结构、必填与可选、模型内外字段、精度及范围、同步/异步、在线/离线、回复成功/失败/超时；验证准确设备载荷、关联结果和拒绝后无下发 |
| 组件编排 | 组件类别和输入输出契约、线性/条件/并行等实际支持拓扑、空或边界集合、类型连接、上下文传递、错误传播和补偿；验证最终业务结果、分支选择和副作用 |
| 动态查询 | 实际支持的字段/运算符/聚合、空/单/多值、时间区间、类型组合、过滤与分页交互；验证结果集及隔离 |

这些是选取维度的参考，按项目能力裁剪。不得为覆盖案例发明产品不支持的协议、拓扑或字段，也不把不受支持的结构预期为成功。

## 跨项目联合交叉覆盖

沿生产者→传输/消费→状态或数据落地→查询/命令反馈建立旅程候选，而非按仓库各写一套CRUD便宣称联合覆盖。先核对真实调用者和数据消费者，包括网关、消息、协议、缓存及异步任务。候选按业务重要性、服务边界转换、状态变化、失败影响选取，明确选中和未覆盖的链路。

每条旅程：

- 用同一测试业务ID/关联ID追踪上下游，记录步骤依赖及数据/状态的传递关系。请求使用实际服务入口；协议模拟或消息输入作为明确的驱动与观测，记录在步骤action和observations中。
- 至少在消费方验证结果，核对字段转换、关联、租户及状态；异步流程使用有界结果等待。生产端返回成功、收到ACK或仅查缓存都不能代替真正的消费断言。
- 对适用的拒绝、超时、重复、乱序、部分完成和恢复选择失败旅程，核对错误传递、无错误成功记录、幂等及补偿。先修复所有上游前提，使目标失败确实发生在声明步骤。
- 多服务资源由一个联合suite持有账本和清理责任，按`owner_service+resource_kind+准确ID`区分，清理suite与步骤保持一致。逆依赖清理及独立sweep仍实际执行；其他suite的共享case映射不授予其账本清理权。

跨服务旅程可以复用已有业务case；接口独立场景与联合旅程分别标识，避免用联合成功掩盖某个接口的负例缺口。业务上不涉及跨服务或本轮只授权单模块时说明依据；未纳入的联合旅程明确为范围外或待覆盖。

## 可执行计划与校验

复制[非空示例](../assets/api-coverage.template.json)到项目`test/plans/api-coverage.json`，按真实模块替换示例内容。它是设计计划，独立于现有catalog和suite coverage；示例刻意保留partial和未覆盖项，不能直接当作项目验收证据。各字段以示例和脚本检查为准：

- `sources`记录来源、版本、内容指纹及位置；`inventory`列服务、included和带理由/source_ids的excluded。接口稳定键为`service:METHOD:/route-template`，同一接口只登记一次。
- `positive_scenarios/negative_scenarios`带唯一scenario_id、预期、断言和case_ids；同一接口的独立场景使用不同case，独立case映射不同test声明。同一流程可由一个场景覆盖多个分支，参数化场景须发现为独立test。`negative_review`逐类评估covered/blocked/not_applicable；按该接口实际能力补全适用类别。
- `branches`记录可到达条件、来源、outcome及场景映射。covered关联真实场景，blocked/not_applicable带理由。普通分支不因接口存在动态参数而免除。
- `dynamic_parameters`记录代表维度、选择、必测交互及已知缺口。selected_scenarios引用本接口场景且使用其case；invalid_combination必须关联负例。`required_interactions`带来源和覆盖状态；`excluded_combinations`仅登记契约禁止作为输入构造的组合。
- `journeys`使用按依赖排列的steps、data_links和下游观测，包含失败评估及清理owner。旅程成功与各独立失败场景须使用互不重叠的case_ids及独立test声明，不以同一测试重复计算覆盖。`writes/cleanup`须完整对应，旅程汇总核对服务、资源类型和suite归属。

准备完整Playwright发现JSON，并在新增实现映射就绪后调用：

```bash
python3 <skill>/scripts/api_coverage.py \
  --project <backend-project> \
  --plan <backend-project>/test/plans/api-coverage.json \
  --catalog <catalog-root>/test/plans/catalog.json \
  --coverage <backend-project>/test/plans/coverage.json \
  --suite-id <suite-id> \
  --discovery <complete-playwright-list.json> \
  --openapi console=<console-openapi.json> \
  --openapi records=<records-openapi.json>
```

`--openapi SERVICE=JSON`可重复，仅读取本地OpenAPI3.x/Swagger2.0JSON快照。工具比较该服务全部operation与included/excluded的差集，并要求来源引用原字节SHA256；scope外operation给出排除依据。路径与OpenAPI paths口径一致，网关前缀映射另记来源。路径项引用先在导出阶段解析；不靠跳过`$ref`获得空差集。无机器契约时省略该参数，工具只验证已声明清单，人工盘点及“接口完整性未机器核对”的限制仍保留。

设计期可省略discovery检查case映射；未落地的场景仍可留在模块设计文档，校验器会将无有效实现视为错误，不能用占位valid消除缺口。编码完成后，在受影响测试派发前和计划/实现/契约变化后由项目runner调用校验入口，复用输入未变的检查结果。已有回归不强制迁移；仅安装skill不会让旧runner自动接入。

退出0表示声明与映射检查通过，退出1表示无效/矛盾的计划或映射，退出2表示已声明缺口。已获准的部分覆盖可用`--allow-known-gaps`在输出缺口的同时退出0；不能把partial改成complete掩盖缺口。`checked`不表示执行通过。输出分开列接口、正负场景、分支covered/blocked/not_applicable、动态代表及旅程数量；pairwise/full按声明约束实际计算遗漏组合，组合空间超过100000时要求缩小分区或改用risk_based。

工具检查结构、引用、有限组合和契约差集，不能证明来源盘点没有遗漏、测试真正到达分支或断言足够。代码审阅负责这些语义，真实Playwright报告负责执行结果；不同来源的覆盖比例分别报告分母，不以单一“覆盖率100%”替代。
