# API自动化

用于对已启动的本地服务或部署环境执行真实HTTP测试。采用项目本地Playwright的request fixture/APIRequestContext；不把单元测试、进程内控制器测试、模拟响应或源码分析登记为真实API通过。既有回归直接走公共快车道，不重新要求阅读全部源码。

涉及资源清理、共享配置恢复或敏感响应处理的fixture变更，按职责执行[离线行为契约](fixture-contracts.md)，使用真实fixture和故障注入验证，再接入实际runner的派发门禁。只读或无相关职责的fixture不强制实现全部契约；合成HTTP验证不计为业务API通过。

## 来源、阅读与用例设计

先读本轮需求与已有共享case，再定点追踪后端入口：实际路由/网关前缀、认证与权限、DTO/校验、业务处理、持久化或外部调用、异常到HTTP/业务码的映射。按需读调用链，不扫描整个后端或把全部方法机械转成case。OpenAPI、接口文档与代码相互补证；源码版本、服务部署版本及观察环境分别记录。

需求未涉及但代码有明确约定的边界可登记为代码派生候选，来源用`kind=backend_code`并提供`location`及revision/fingerprint。预期记录依据和适用版本，审核后才能计入覆盖；实现与需求冲突时登记待澄清项，不改断言迎合实现。没有源码时可按需求和接口契约继续黑盒测试，明确无法核对的实现分支。

优先复用业务case ID、来源和业务预期，只新增本suite的实现映射。需要新增API覆盖类型时，在原授权范围内更新case.required_kinds；UI/API专属场景单独建case，不要求每个case都实现两次。公共`exploration`阶段在API中表示定点代码/契约阅读，`exploration_action=executed/reused/not_needed/blocked`记录真实动作，不伪造页面探索。

先跑通一个代表流程及清理，再扩展获准范围。按需求选择正常、参数边界、业务约束、权限/租户隔离、幂等、状态转换及异步结果；不默认授权负载、破坏性、安全攻击或生产写入。

### 逐模块补全覆盖

新增API用例或补齐模块时，先读取[覆盖设计与缺口校验](api-coverage.md)，建立逐接口正负例、有限业务分支、动态代表组合和跨服务旅程的映射，再编码。普通分支尽可能逐项覆盖；动态输入空间按契约选典型值、边界及风险交互，有限控制分支仍逐项核对。前端用例作为业务来源，接口和场景清单以需求、后端契约及实际处理链补全。

使用`scripts/api_coverage.py`核对独立的`test/plans/api-coverage.json`与catalog、API实现及完整Playwright发现；提供本地OpenAPI快照时再核对接口差集。项目runner在新增实现就绪后、派发前接入，未接入时明确限制。缺口、设计映射和真实执行分别报告，不能用少量代表流程已通过宣布完整覆盖。

用户要求补齐API场景时，按模块核对实际入口→输入与校验→业务处理→持久化或外部调用及有效需求，沿项目实际结构定点阅读，在模块计划中维护“接口/业务分支、依据、已有case、新增case、待覆盖原因”的对应表。每个模块先跑通代表流程及清理，再补齐其余获准场景；独立模块在配额允许、写集及资源无冲突时可并行推进。阻塞分支保留原因与依赖，继续其他独立目标。用例条数作为执行规模记录，不作为覆盖充分的依据。

- 参数核对区分缺省、null、空字符串、空白、边界值和类型，仅为实际契约不同的分支建case；新增与编辑校验分别核对，编辑拒绝后回读原值及关联，验证事务没有留下部分修改。
- 业务核对包含唯一性及其作用域、引用删除阻断、状态往返、删除后访问、筛选交集和分页；涉及权限时同时核对读取与写入拒绝，账号具备的实际权限以配置和代码为准，不从“管理员”或租户名称推定。
- 各自可能失败的场景注册为独立test，可用参数化共享实现。同一test内的循环适用于同一业务流程的多步回读；不同拒绝条件分别报告，避免前一个失败遮住后续结果。
- 需要外部系统、特定身份或共享配置的分支列明依赖；保留未覆盖原因和代码与需求差异，不用浅层参数检查替代业务流程覆盖，也不为补数量重复断言。

### 执行依赖与状态准备

编码和执行前区分资源依赖、配置前提及执行次序，在模块计划写清准备、业务动作、回读和逆依赖清理。按实际依赖分段交付；每个case通过自身fixture准备所需资源与状态，不依赖前一case成功或遗留的数据。模块顺序不能替代case内依赖管理。

用户已经授权切换专用测试scope内配置时，由fixture保存原值、登记intent、设置并回读所需状态，业务资源清理后恢复原值并回读；不要把可自动准备的开关状态变成每例重复失败的人工前提。相关case显式声明需要的配置值，开启和关闭路径分别执行。授权限定的scope保持精确，其他租户或系统域不能沿用该写权限。

配置写入与读取其状态的业务流程共用冲突组，跨UI/API复用实际协调目录、冲突键和系统级锁协议；两个工程各自建锁不能证明共享配置已互斥。保持容量配额与资源冲突分开，复用已验证会话，避免为模块拆分重复登录。清理及恢复只接受本工程或显式继承的归属账本，其他suite的恢复标记保持不变。已恢复配置的历史账本保留当时回读证据，后续sweep只恢复未决项，不把其他任务后来合法变更的状态重置为旧基线。

## 工程与环境

`PROJECT`选实际后端测试工作区，默认保留工程的`test`目录。沿用已有Node包、Playwright配置、testDir和脚本；后端已有JUnit/pytest不等于已具备Playwright HTTP runner，不改写它们，不为HTTP测试启动浏览器。只在真实认证流程需要时另行检查和领取浏览器占用。

在忽略配置或CI密钥中加载baseURL、身份profile、租户/组织上下文和凭据，Git配置只写引用。先确认测试环境、服务版本、数据权限及必要依赖，运行实际Python/Node/产物路径探针；服务不可用只阻塞相关目标。启动或部署服务沿用现有授权，普通测试请求不包含发布授权。

独立suite配置、共享case和迁移见[套件契约](suites-and-cases.md)。调度请求沿用suite.kind，直接回归可显式传`test_kind=api`；worker数按实际CLI声明。API worker消耗worker配额而非浏览器配额，HTTP并发仍受账号池、限流与业务资源冲突约束。浏览器登录单独以UI任务领取配额，不借API模式绕过占用。

API用例具备独立资源、身份会话隔离及可并发的配置锁契约时，可按测得的后端容量增加Playwright worker；配置只读锁使用操作系统共享锁时，仍须与UI/业务配置写入的独占锁互斥。不能仅调高CLI worker而漏改Attempt计划及worker配额；runner应限制可配置上限，并通过真实跨进程锁测试验证读读并发、读写互斥和异常退出释放。按真实执行时间区分登录准入、业务CLI与清理sweep，再决定优化层次。

### fixture与证据处理提速

按实际校验链准备最小依赖。DTO或空目标等在资源查找前拒绝的场景，可直接发送真实请求；不存在目标查询按契约提供准确唯一ID，无需创建其他无关资源。物模型、资源关系、状态及租户隔离仍准备其业务依赖。避免统一beforeEach给纯参数负例创建整条业务资源链，保留独立test及原有断言。

区分业务请求与本地证据开销。批量同步应完整预校验输入后，按资源保留归属及readback证明，合并加载和写入共享索引、工作流状态；逐账本重放同一大状态不算真正合批。意图先登记、未知结果和清理失败及时桥接，成功缺席可在本地证据已落盘且旧未决门禁仍保留时合批提交。离线验证覆盖异属账本、重复身份、部分清理失败及桥接失败，不能因合批提前释放占用。

协议模拟器连续请求复用已建立连接。配置变化会异步断连时，等待真实断连事件后再建新连接，并按业务消费结果完成屏障；仅回读配置或握手成功不足以确认旧连接已失效。业务上报失败保留原意图和未知结果，按项目幂等契约恢复，避免在通用发送函数中无条件重连重发。

连接已明确关闭时，在登记业务发送意图前检查并拒绝，避免为尚未尝试的发布制造未知写结果；预检不能消除实际发送期间的断连，已经尝试发布的意图继续保留。错误码保持稳定，诊断细节通过cause或独立字段提供，离线检查同时核对原有错误断言。并发执行中，清理失败阻断同一资源域的后续造数，活跃case完成自身清理；共享残留门禁不把其他活跃case正常持有的资源误判为清理失败。

代表流程失败时暂停扩展并诊断；进入完整回归后，普通业务断言失败默认继续无依赖的case，避免全局首错中止反复重跑已通过场景。资源清理未决、认证失效或共享前提损坏仍按实际影响阻断派发。性能比较使用同一组case的耗时及独立sweep计时，明确并发case耗时之和与CLI墙钟耗时的区别，保留失败、中断及未执行结果。

## 请求、断言与清理

- 使用request fixture或独立APIRequestContext，按身份/worker隔离认证和上下文；自行创建的context在finally/fixture teardown中dispose。Cookie或token变化按项目规则传播，不在不同身份间误用状态。
- 同时核对HTTP状态、响应shape/业务码及需求中的字段和状态变化。分别从项目公共响应封装、异常枚举及认证/异常处理链确认两层状态的映射，权限拒绝的业务码不预设等于HTTP 401/403。HTTP 200不必然成功；错误响应应成为可断言的数据，不能仅因抛错而失去预期拒绝的证据。
- 字符长度先区分UI输入限制、业务长度约束、API校验上限和数据库容量，按需求与接口契约确认各自适用范围及计数口径，验证边界值及新增、修改后的回读完整性。数据库预留容量不放宽业务上限；仅在已明确确认该产品长度限制只约束UI、API允许更长输入时，才不把超出UI限制被接受单独判为缺陷。契约有歧义时登记待澄清，不从实现或存储容量反推业务预期；本地代码或SQL修复与环境部署、升级及HTTP复测分别记录。
- 按实际接口解析分页层级、默认筛选与更新字段。详情、普通分页和带统计的列表可有不同封装；“准确ID不存在”和“已存在但属于其他租户”也可能走不同错误分支。更新测试沿用契约要求的原状态值，先追踪校验及SQL再判断是否产品失败。
- 写入前登记资源意图；创建后绑定准确服务端ID和所有权，查询回读，再逆依赖清理并验证实际缺席。超时、断连或5xx后先核实创建结果，不盲目重发写请求。
- 异步场景按需求定义的状态与时间预算有界轮询；不固定sleep替代结果断言，不把最终一致性当作立即成功。就绪谓词应覆盖目标记录或状态本身，不能只检查total/count等聚合值：列表与计数分开查询时，计数可能先反映新写入而列表仍为空或不完整。幂等请求使用项目真实支持的机制，不为测试发明服务端不接受的header。
- 未授权/无权限、查询失败和真正不存在分别判断；404也须核实路由、身份和业务契约，不能统一当作资源已删除。清理失败继续保留占用/残留门禁。
- 业务数据只使用明确授权范围；身份、共享配置及跨工程资源沿用[清理契约](cleanup.md)与[共享协调](suites-and-cases.md#资源协调)。
- 批量写操作返回后，在fixture清理前回读准确目标及受保护对照，分别核验成功项、失败项和原关系；teardown或sweep补偿成功只证明最终清理，不能替代批量接口本身的业务断言。

## 执行、诊断与交付

使用真实选择参数`--list`，准备独立Attempt，再执行原生JSON/HTML/blob reporter；保留retry/repeatEach/project语义。现有进度reporter可直接用于API，Setup仍显式区分；不为进度安装checkpoint或禁用重试。按[进度汇报](workflow.md#进度汇报与长任务等待)向用户报告阶段、已结束/总数、失败、阻塞、清理和报告阶段。

按实际请求链诊断失败：先核对测试契约、认证/上下文、载荷、服务端相关代码与部署版本，再区分脚本、产品及环境问题。已确诊的产品问题记录后继续其他独立目标；测试/fixture修复自行推进，业务修复另依授权。`work_packages`显式传`test_kind=api`时，API专属项进入`diagnose_api`，不交出本技能。

原始响应、附件和日志可能包含凭据或个人数据；项目runner先按既有规则脱敏，避免输出认证header、完整请求对象和敏感响应。创建或详情返回业务密钥时，首次落盘前按白名单提取清理所需ID及归属审计；原始密钥仅留内存，负例意外成功、附件、bridge和恢复链同样处理。验证密钥格式、唯一性或不变性时使用不打印密钥值的断言。仅登记安全证据路径。报告区分HTTP实际执行、代码阅读、替身证据、未到达分支及清理状态；API通过不表示UI通过。
