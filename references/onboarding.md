# 首次接入：从前端工程到第一条真实用例

用于首次建立Web UI测试体系、迁入本技能或用户明确要求重新配置。已有回归、来源快检和按报告修复不重走本流程；配置变化只补受影响项。以下为Agent引导流程，不是新增CLI能力。

## 1. 定位工程并补齐资产

- 先查看当前工程约束、Git状态、包管理器锁文件、工作区、项目脚本、Playwright配置及已有测试。优先把`PROJECT`选为实际前端包目录；monorepo若统一在根目录管理E2E，则沿用其既有根目录和命令cwd。多个候选无法判断时再询问，不把技能安装目录当成待测工程。
- 若当前只有后端仓库，询问前端工程路径；纯黑盒测试可经确认使用独立E2E工程，不要求创建或克隆前端/后端仓库。不要为了初始化移动已有测试或覆盖用户配置。
- 确认路径与本地初始化意图后，使用已核实的Python 3.10+运行以下命令。`SKILL_DIR`取本技能实际安装目录，`PROJECT`取上述工程目录，不照抄示例路径。

```sh
python3 "$SKILL_DIR/scripts/workflow.py" init --project "$PROJECT"
```

Windows使用已核实版本的`py -3`或项目Python及对应shell路径语法。`init`仅创建缺失的`test/spec.md`、`test/plans/coverage.json`并保留已有文件；不安装依赖、不生成Playwright配置或测试、不修改`.gitignore`、不读取线上文档，也不启动run或浏览器。已作为工作流配置的spec缺配置块时在原文件补齐，不能用模板覆盖。

工作流元数据固定使用上述文件和`test/.cache/`；已有测试、fixture、Playwright配置及cwd沿用项目布局，`test/src/`仅为新工程建议，以coverage的spec/plan、真实发现及Attempt的cwd绑定。直接回归不要求初始化；调度可用项目相对Markdown的[config_path](contracts.md#双预算与就绪任务)，或显式null跳过无关test/spec.md，规范配额账本和残留索引仍共享同一PROJECT。

## 2. 引导填写项目输入

先复用可发现的项目脚本、已有文档与已确认答案，只集中询问真正缺少的内容；不要要求用户一次填写完整测试设计。可用以下清单引导，允许逐项补充：

| 输入 | 引导问题及处理方式 |
| --- | --- |
| 需求来源 | 权威需求文档的线上地址或本地文件是什么？涉及哪些模块、版本与附件？多个来源说明优先级；尚无正式文档时，请用户确认可作为预期的产品说明，不以当前页面或代码自动代替验收标准。 |
| 环境与启动 | 测试哪个环境、页面入口和部署版本？本地服务是否需要启动、使用哪个现有命令？启动、部署和访问权限分别确认，不假定有后端管理权限。 |
| 代码定位 | 前端工程与测试命令cwd从工程确认；后端代码库路径、分支/版本仅在追踪接口、fixture或诊断需要时收集，可填“不提供/纯黑盒”。本地源码不等于线上已部署版本。 |
| 身份与数据 | 是否登录、有哪些测试角色、凭据从哪里加载？专用环境/租户/组织范围、可写资源和清理方式是什么？无登录则明确记为无；不要求用户在对话粘贴密码、token或Cookie。 |
| 首轮目标 | 最想先验证哪个模块/用户流程？已有用例是否复用？按[授权复用](workflow.md#授权复用与自动推进)直接登记用户已明确的范围；缺少决定时再给候选及建议供选择。 |

填写`test/spec.md`时沿用[现有配置契约](contracts.md#git资产)：需求映射到`source`，环境/认证/数据策略/命令映射到`env`、`authref`、`data-policy`、`commands`，确认范围写入`scope.fixed/modules`。后端路径和接入说明写入模板的说明区，不创造新的必填JSON字段。未知值保持待确认，不能填占位值冒充配置就绪。

文档URL、环境入口和本地绝对路径可能暴露内部信息。受限值存入经核实已忽略的本地配置，Git资产仅保留来源标识、profile引用及项目实际加载入口；引用必须确实能由当前读取工具或项目runner解析，本技能不会自动解析任意自定义引用。来源正文、认证、截图及运行产物不得写入公开模板。拟公开的项目特有内容无法判断是否可公开时先询问用户。

## 3. 按阶段检查依赖并提示安装

依赖检查由Agent按当前阶段执行；直接回归不要求ego-browser或需求来源读取工具。`doctor`只诊断工作流资产、配置及缓存Git忽略/索引状态，**不替代工具、浏览器及登录检查**。一次汇总为“可用/缺失/未验证/不适用”，区分技能已发现、命令能运行、宿主集成可用和实际访问成功。

| 检查项 | 检查与缺失处理 |
| --- | --- |
| Python | 最低3.10；核实实际解释器版本与路径，同轮辅助命令固定使用该解释器。本技能脚本只用标准库，入口自动拒绝低版本；缺失则使用已有兼容解释器，或按授权安装，不擅自替换系统默认Python。 |
| Node与包管理器 | 按工程的版本约束、锁文件和`packageManager`核实运行时与命令。缺失时给出匹配项目的安装建议，不擅自更换包管理器或重建锁文件。 |
| Playwright | 从测试所在工作区检查本地依赖、配置、runner及版本；优先复用已有package脚本，不因全局命令存在就认为项目已配置。避免用可能自动下载的`npx`等方式探测。缺失时按项目包管理器安装/补充依赖；改manifest、安装包复用相应有效授权，缺授权时才征询。 |
| Playwright浏览器 | 核对配置选择的浏览器/channel、可执行文件或Playwright缓存及系统依赖。CLI版本可读不证明浏览器能启动；就绪后再做最小启动验证，未验证前如实标记。缺失时使用已安装的项目Playwright安装入口，复用已有下载/系统依赖安装授权，并遵守宿主审批；缺授权时才征询。 |
| ego-lite探索 | 新增页面探索默认使用ego-lite，该阶段才检查`ego-browser`技能、命令并按技能运行`ego-browser skill`。CLI来自ego-lite，不猜测存在名为`ego-lite`的命令。缺失时按已有安装授权及该技能指引处理，需人工完成的应用首次引导再交用户；应用入口为[ego-lite官网](https://lite.ego.app/)。宿主连接和真实页面访问仍需后续验证。 |
| 资料读取工具 | 只有来源需要时才检查：WPS链接确认当前可用的`wps365-docs`技能及其实际CLI入口；安装与使用说明见[WPS 365 插件仓库](https://github.com/YiuTerran/dsh-wps365-plugin)。其他云文档、本地Word/PDF等用对应可用读取方式。不能以WPS CLI不在PATH就判定未安装，按其技能定位。缺失则提示安装对应技能/工具，或请用户提供可读导出；不强迫所有项目安装WPS依赖。 |

安装工具/依赖、修改manifest及下载浏览器时先核对已有授权；授权仍适用则连续完成并验证，不重复征询，宿主文件/命令审批照常遵守。真正缺授权或需要人工完成首次引导、资料授权和业务登录时，再提示缺什么、阻塞哪个阶段、具体动作及验证方式。资料工具存在不代表有权限，认证失败按该工具当前指引处理，不猜测过期、不绕过权限。

缺浏览器时可先整理需求，缺资料权限时可先准备工程；不可将未读文档标为已核验或把未启动的浏览器记为成功。WPS不是来源时标“不适用”，没有后端代码不是黑盒UI测试的阻塞项。

### 运行前提与兼容性

辅助脚本最低要求Python 3.10；版本满足要求与运行时兼容是两项检查。实际解释器路径、版本见[运行时探测](local-tools.md#运行时探测)的`python_runtime`；不要仅凭终端名称、venv名称或宿主声称的版本判定。切换解释器后，按当前环境重新探测。

回归需在允许创建约定产物目录、正常使用锁及原子替换的执行环境中运行，可以是兼容的受管shell或已授权宿主终端。`preflight`会检查Python文件操作，Node探测需提供项目实际可执行文件；默认目录通过不证明其他路径可写，首次长回归前再针对实际Attempt输出父目录探测。探测不启动浏览器，浏览器启动与业务访问仍按各自检查完成。

`fs_mkdir_not_idempotent`表示当前运行时对已有目录的`mkdir(exist_ok=True)`不符合幂等约定；产物目录创建被拒属于权限或路径策略问题，提高Python版本或目录预检查不能保证解决。保留原错误及发生阶段，暂停受影响派发，通过宿主支持的授权或兼容性修复处理；需要改用宿主终端时在原授权范围内执行并复检，不由技能绕过。

保留`PYTHONPATH`、`NODE_OPTIONS`等继承环境，它们可能包含项目导入路径、内存参数或宿主集成。技能不自动移除注入、不切换产物根来规避策略；目录兼容处理只复用确实存在的目录，权限错误继续抛出。执行中仍可能发生后续权限拒绝，预检通过不是全程可写或回归成功的保证。

## 4. 检查配置并梳理需求

1. 写入真实来源快照、认证或run证据前，核实`test/.cache/`被Git忽略且无文件进入Git索引；需要时补`/test/.cache/`并检查反向规则。`workflow.py doctor --project "$PROJECT"`会检查配置、忽略规则及缓存索引状态；忽略规则不能清除已跟踪文件。它不批准业务范围，也不证明外部依赖就绪。
2. 通过来源对应工具读取本轮相关正文及附件，保留实际版本、范围和可比证据；不可读部分标未知。代码用于理解实现/接口链路，不把实现偏差写成需求预期。
3. 按模块整理“需求→候选case→前置身份/数据→预期→清理”，复用已有caseID和有效资产，列出影响预期或权限的疑点。无法确认的部分不批准；不为首轮代表流程一次性设计大量用例。完整需求验收所需的全量映射不能用局部盘点替代。
4. 给出首轮建议及未选缺口，已有明确原始请求则按[授权复用](workflow.md#授权复用与自动推进)登记，缺少决定时才征询。优先验证可安全执行、能回读和清理的代表流程，再推进全部获准目标；普通初始化请求不等于批准全部新增覆盖、部署或生产写操作。完整非空清单就绪后登记原话和原始依据，明确全部覆盖内的新缺口更新登记，不重复审批。

## 5. 带用户进入第一轮用例

范围和必要输入就绪后，转入[工作流](workflow.md#最小命令顺序)，用`preflight`创建/接管run，真实登记来源与审批，不为问参数提前持有run租约。按已有门禁完成：

**获选需求与预期确认→ego-browser真实探索→独立Playwright用例和必要fixture→定向执行→回读/清理核验→报告与下一步。**

同一探索者完成代表场景编码；发现产品差异保留需求断言，不擅自修业务或降低断言。先跑通代表流程，再在已获准范围内扩展；收尾回归与报告绑定仍遵循原工作流，不以首条用例通过宣称全量需求通过。

阶段交付只需一份简短就绪清单：工程位置、已确认输入、依赖状态、未决问题、获选首轮case，以及下一步由谁做什么。若仍阻塞，给出可继续部分与确切待办；以后复用此配置，只刷新变化项，不要求用户反复填写。
